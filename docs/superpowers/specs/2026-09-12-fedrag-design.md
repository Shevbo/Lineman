# fedrag — канон федерации через RAG на sdev

Дата: 2026-09-12
Автор: Клод (инженер инфраструктуры федерации)
Статус: спека на ревью у Бориса

## Задача

Перевести документацию федерации из режима «копия канона в каждой папке агента» в режим
«запрос к общему индексу», поддерживать её актуальной автоматически и переписать онбординг
и личности агентов под новый способ доступа.

## Что уже есть (замерено 2026-09-12, не предполагается)

RAG **уже развёрнут** и работает. Ничего нового не строим, достраиваем существующее.

| Компонент | Факт |
|---|---|
| Сервис | `ragkit`, хост sdev, `~/ragkit`, systemd `ragkit.service`, uptime 1д17ч |
| Порт | `127.0.0.1:8791`, loopback only, в коде явно «never exposed off-box» |
| Индексы | `index/stl.db` 54 MB, `index/federation.db` 6.5 MB |
| Корпус федерации | `corpus/federation`, 6.9 MB, 169 md |
| Синк канона | `ragkit-fedsync.timer`, каждые 20 мин, `scripts/sync_federation.sh` тянет со smain по ssh |
| Реиндекс | `ragkit-reindex.timer`, каждые 15 мин, инкрементальный |
| Модель эмбеддингов | `intfloat/multilingual-e5-large` |
| Реранкер | `jinaai/jina-reranker-v2-base-multilingual`, `rerank_top = 30` |
| Клиент | `ragkit/server.py`, MCP stdio, ходит по ssh из окон VS Code |
| RAM демона | RSS 3.6 ГБ из 8.9 ГБ на sdev, свободно ~3.9 ГБ |

Качество выдачи проверено живым запросом: возвращает путь файла, цепочку заголовков,
номера строк и score. Попадание точное.

### Замеренная латентность

Три последовательных запроса к живому демону:

```
порядок эскалации инцидента     -> 24.03 s
где лежат логи Lineman          -> 20.81 s
что такое pre_approved          ->  6.16 s
```

### Замеренная конкурентность

`ragkit/httpd.py` обрабатывает запросы под `with _lock:` — строго по одному.
Комментарий автора в коде:

> cheap to queue at STL's human-paced query rate. Upgrade to a session pool if a queue
> shows up under load.

Федерация и есть та нагрузка, о которой предупреждал автор.

## Чего не хватает

1. **Агенты не могут спросить.** Демон на loopback плюс ssh. hoster, vibe, pi доступа не имеют.
   Сегодня это инструмент окон разработки, не федерации.
2. **Латентность 6-24 с и сериализация.** 14 агентов в очереди по одному дают минуты ожидания.
3. **Корпус неполный.** `sync_federation.sh` тянет только `~/*.md`, `~/docs`, `~/memory` со smain.
   Не попадают: `~/workspaces/*/AGENTS.md` (30+ файлов, личности агентов),
   `~/.claude/projects/*/memory/`, `federation_registry.json` (44 узла),
   `config.json -> agents.node_map`, инциденты Lineman из `.claude/memory/`.
4. **Онбординг не тронут.** `/onboarding` по-прежнему копирует 40 KB канона в папку агента.

## Решения, принятые Борисом

- **Граница статики и RAG:** карточка агента плюс аварийный минимум, около 4k токенов.
  Всё остальное уходит в RAG.
- **Транспорт:** через Lineman, новый endpoint `/api/fedrag/search`. ragkit остаётся
  на loopback, замысел автора не ломаем.

## Архитектура

```
агент (любой узел федерации)
  |
  |  POST http://10.66.0.1:9090/api/fedrag/search
  |       {"query": "...", "depth": "snippet"}
  |       X-Agent-Name: <agent_id>
  v
Lineman :9090
  |  - учёт агента в request_log
  |  - кэш ответов (канон меняется редко)
  |  - рейт-лимит на агента
  v
sdev:8791 через WireGuard
  |
  v
ragkit httpd -> federation.db (+ stl.db для профильных агентов)
```

### 1. Латентность и параллелизм (делается первым, до раскатки)

Цель: медиана ответа **под 2 секунды** на запросах к канону.

Работы:
- Снять сериализацию: пул сессий вместо глобального `_lock` в `httpd.py`.
- Отдельный лёгкий профиль поиска для запросов канона. Модели кэшируются
  в `embed._MODELS`, второй `Searcher` на тех же весах дополнительной RAM не стоит.
- `/search` сейчас принимает только `query` и `depth`; параметры реранка зашиты в конфиг
  на момент загрузки. Добавить выбор профиля в запросе.

**Гипотеза, требующая замера, а не объявления:** основное время съедает реранк 30 кандидатов
кросс-энкодером на CPU. Перед изменением параметров профилировать вклад эмбеддинга и реранка
раздельно. Если гипотеза не подтвердится, план этого пункта переписывается по факту замера.

**Критерий приёмки.** В ragkit есть готовый harness качества поиска: `tests/eval.py`,
50 эталонных вопросов в `tests/questions.jsonl`, `questions_audit.jsonl`,
`questions_third.jsonl`. Он считает recall@1, recall@3, латентность и стоимость в токенах.

Порядок: снять baseline на текущем демоне, внести правки, прогнать снова.
Ускорение принимается только если recall@3 не просел. Падение recall ради латентности
не размен, а поломка: агент получит быстрый неверный ответ вместо медленного верного.

Без выполнения этого пункта раскатка на агентов не начинается.

### 2. Транспорт: `/api/fedrag/search` в Lineman

- Новый endpoint в `reverse_proxy.py`, проксирует на `sdev:8791` через WG.
- Читает `X-Agent-Name` / `X-Lineman-Agent`, как остальные маршруты.
- Пишет в `request_log`: агент, запрос, латентность, число чанков.
- Кэш ответов с TTL. Канон меняется раз в сутки, повторные запросы агентов будут частыми.
- Рейт-лимит на агента, чтобы один зациклившийся агент не занял единственный демон.
- Деградация: sdev недоступен -> внятный ответ агенту «RAG недоступен, смотри карточку»,
  а не таймаут.

### 3. Корпус

Расширить `scripts/sync_federation.sh`:
- `~/workspaces/*/AGENTS.md` и `~/workspaces/*/CLAUDE.md`
- `~/.claude/projects/*/memory/`
- `federation_registry.json` (44 узла)
- `config.json -> agents.node_map` (только карта агент/узел, без `proxy_pool`)
- `.claude/memory/04_incidents.md` из Lineman

**Секреты.** `configs/federation.toml` уже исключает `**/.env*`, `**/secrets/**`,
`**/credentials*`. Перед добавлением каждого нового пути проверить, что он попадает
под эти исключения; `config.json` синкать только частично, секции с credentials не трогать.
В индекс не должно попасть ни одного значения секрета, только имена переменных.

### 4. Онбординг и личности агентов

`/onboarding` перестаёт копировать канон. Вместо снимка на 40 KB пишет карточку ~4k токенов:

- identity: `agent_id`, `node`, назначение, путь репозитория
- `node_map`: WG-адреса узлов
- inbox/reply: готовые curl-шаблоны
- STRICT-правила: LLM только через Lineman, секреты только через Ключника,
  новый persistent-ресурс -> `fed-backup`, не спавнить `claude -p`
- порядок эскалации при инциденте
- одна строка: `curl -s 10.66.0.1:9090/api/fedrag/search -d '{"query":"..."}'`

Сам канон остаётся источником правды на smain и индексируется.

Раскатка волнами, не всем сразу: сначала один агент, замер по `request_log`, потом остальные.

### 5. Актуальность

`fedsync` 20 мин и `reindex` 15 мин уже стоят. Правило в роль куратора: любая запись
в канон попадает в индекс максимум за 35 минут, руками ничего не делается.

## Ожидаемый эффект (честно)

- **Гарантированно:** пункт 4 снимает порядка 11k токенов со старта каждой сессии каждого
  агента. Сейчас агент грузит снимок канона ~13k токенов плюс свой `AGENTS.md` на 2-4k.
  После правки остаётся одна карточка ~4k, вобравшая и то и другое.
- **Не гарантировано:** пункты 1-3 сами по себе токены не экономят. Агент платит за запрос
  и за выданные чанки. Выигрыш в том, что агент находит ответ вместо чтения трёх файлов
  целиком или переспрашивания. Это качество и скорость.
- Мерить по `request_log` до и после раскатки, а не обещать процент заранее.

## Порядок работ

1. Латентность и параллелизм ragkit (блокер)
2. `/api/fedrag/search` в Lineman
3. Расширение корпуса и проверка исключений по секретам
4. Переписывание `/onboarding` под тонкую карточку
5. Раскатка по агентам волнами, замер эффекта

## Риски

- sdev 8.9 ГБ RAM, демон уже держит 3.6 ГБ. Пул сессий поднимет потребление,
  запас ~3.9 ГБ надо контролировать, иначе получим на sdev тот же OOM,
  из-за которого ragkit не поставили на smain.
- ragkit единственный демон. Его падение ослепляет всех агентов сразу — отсюда
  требование аварийного минимума в карточке и внятной деградации в Lineman.
- Изменения в `httpd.py` и `search.py` затрагивают рабочий STL-индекс.
  STL не должен пострадать: прогон `tests/eval.py` и `tests/test_incremental.py`,
  `tests/test_server.py` до и после правок.
- `~/ragkit` на sdev лежит внутри git-репозитория уровня `/home/shevbo`, своего репозитория
  у сервиса нет. Перед правками сделать копию рабочей версии, чтобы был откат.
